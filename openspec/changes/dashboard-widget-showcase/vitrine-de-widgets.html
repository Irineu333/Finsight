Por que mexer

Hoje o editor é uma LazyColumn com um estado da reorderable 3.0.0: os ativos em cima, um cabeçalho "Disponíveis" no meio e os desativados embaixo a 60% de opacidade. Ativar e desativar são reordenar — arrastar para baixo do cabeçalho desativa. O cabeçalho e os dois vazios existem como chaves-sentinela só para servirem de alvo de drop.

  • Toda a aritmética mora em DashboardEditLayout.move(fromKey, toKey): cinco ramos, três sentinelas, um activeCount como fronteira. DashboardEditLayout.kt:22-63
  • Catorze tipos de widget, cada um renderizado em tamanho real na lista — a tela fica longa, e metade dela é o que não está na dashboard.
  • A reorderable é usada só nesta tela. Nenhum outro arrasto existe no projeto.

A restrição que decide tudo. Um ModalBottomSheet do Material 3 é outra raiz de composição — o próprio código paga esse preço com Modifier.exposeTestTags() em cada sheet, "a sheet is its own composition root" (ModalManager.kt:159). O ponteiro não cruza essa fronteira em plataforma nenhuma. Se o arrasto tem de entrar e sair da vitrine, a vitrine não pode ser modal. No desktop isso já é verdade de graça: o DetailPane é irmão do conteúdo no mesmo Row (ChromeHost.kt:273, 345).

A ideia

Três gestos, uma metáfora: a vitrine é a fonte, a lista é a dashboard. Arrastar de uma para a outra adiciona; no sentido contrário, remove; dentro da lista, reordena. O código já chama a vitrine pelo nome — showcase (DashboardComponentType.kt:10).

Apagado, por um motivo

Em modo edição, um card apagado diz uma coisa só: "só no celular" / "só no desktop" — o tipo não se mostra neste WindowMode (DashboardComponentVariant.modes). Vale para o card na vitrine e para o item na lista: um widget ativo que não renderiza nesta janela aparece apagado no editor, em vez de sumir. Continua arrastável — a dashboard é uma só, e o usuário edita para todos os seus dispositivos.

Detalhes que já estão decididos pelo código

  • O card é o preview real. DashboardComponentVariant.*.Preview e DashboardPreviewFactory.createPreview(key, on) já fabricam o widget com dados fictícios na moeda-base; a lista de edição já os renderiza.
  • A inércia vem de um overlay, não da variante. Um Box.matchParentSize() com clickable + handle de arrasto cobre o widget (DashboardEditingContent.kt:203-213). A vitrine repete a técnica — e o overlay é a fonte do arrasto.
  • O ≡ imediato fica em todo card, vitrine incluída. É o gesto do mouse no desktop e o único que o Maestro executa (swipe from: id:); o corpo espera um long-press.
  • Mesmo breakpoint do painel. isExtraWideWindow() decide sheet ou painel, como já decide para todo AdaptiveModal. Se a janela encolhe no meio da edição, o AdaptivePane é dispensado (AdaptiveDetail.kt:194-200) e a sheet assume.

O modelo

Ordenar e adicionar separados, a chave continua sendo a do tipo, e "disponível" deixa de ser estado guardado: é o que o catálogo tem e a dashboard não.

Hoje
Editing(activeItems, availableItems)
move(fromKey, toKey)      // 5 ramos, 3 sentinelas
availableItems guardado   // e recalculado no VM
Depois
Editing(activeItems)
add(type, at)  remove(key)  move(from, to)
vitrine = catálogo − ativos   // derivada, não guardada

Preferências, repositório e builder não mudam: Preference(key, position, config) continua sendo o que se salva. EditListEntry.SectionHeader e os dois placeholders somem; AddAllComponents e RemoveAllComponents saem.

O motor de arrasto

Com as duas apresentações na mesma árvore, o problema fica bem definido — e é o mesmo nas duas.

core/dragdrop/                                ← módulo próprio, convenção finsight.compose.library
 ├─ DragAndDropHost { content }              ← montado no App ao lado de ModalManagerHost e DetailPaneHost (App.kt:150-151)
 │    ├─ LocalDragAndDropController
 │    └─ overlay do ghost                    ← por cima de TUDO: no desktop o painel está fora da subárvore da tela
 ├─ Modifier.dragSource(payload, ghost)      ← long-press no corpo; imediato no ≡ e no mouse
 ├─ Modifier.dropTarget(onHover, onDrop, onExit)   ← bounds em coordenadas de janela
 └─ autoscroll de LazyListState nas bordas
  • Por que próprio. A reorderable recebe um LazyListState e o arrasto nasce e morre dentro dele; não há "sair da lista". Dois sistemas de gesto no mesmo item disputam o mesmo pointerInput — o item já empilha dois handles hoje. Um dono para os três gestos.
  • Por que não o dragAndDropSource do foundation. É a sessão de arrasto do sistema operacional: sombra do SO, pensada para cruzar apps, sem slot animado nem ghost estilizado. Suporte iOS na CMP 1.10.1 não confirmado — e não mudaria a escolha.
  • O que passa a ser nosso. Autoscroll e a animação de deslocamento (Modifier.animateItem()) — a parte chata, não a difícil. Estimativa: 300 a 500 linhas — grande o bastante para um módulo.
  • O que a lista faz com o hover é dela. Recebe o offset, acha o índice pelos bounds dos itens visíveis, abre o slot. A vitrine é trivial: qualquer hover é "aqui remove".

Por que core/, e não feature/

core/dragdrop
  • Um core é "quem não conhece feature nenhuma" — e o motor não conhece: não tem rota, não tem tela, não tem domínio, não tem Entry.
  • É o mesmo lugar dos seus irmãos: ModalManager e DetailPane moram em core/designsystem, e o host é montado por :app:shared, que vê tudo.
  • Qualquer feature api pode usá-lo — api depende só de :core:*.
  • Módulo separado de designsystem: tem tamanho e testes próprios, e não puxa o tema para quem só quer arrastar.
feature/dragdrop/api — descartado
  • Um api declara "rotas, interfaces de repositório e de caso de uso, o Entry" — nada disso existe aqui; seria um api sem impl só para caber no padrão.
  • Uma feature api não pode depender dele (api ⊄ api), então um componente de core/ui ou de outro api nunca poderia oferecer arrasto.
  • O shell teria de montar o host de uma feature que não é uma seção do app.

Regras citadas de CLAUDE.md (module structure, dependency rule) e feature/README.md.

Como se prova

Unitário

  • DashboardEditLayoutTest (12 casos sobre move e sentinelas) morre inteiro — o que ele provava deixa de existir. No lugar: add(type, at) insere na posição e recusa um tipo já ativo; remove(key); move(from, to); e a vitrine é exatamente o catálogo menos os ativos, na ordem do catálogo.
  • DashboardDeprecatedWidgetTest continua tal qual: "não é oferecido para adicionar" passa a significar "não está na vitrine".
  • Um layout salvo hoje reabre idêntico — nada muda na persistência, e o teste é o que garante que isso é verdade e não intenção.
  • O cálculo "dado o offset do ponteiro e os bounds dos itens visíveis, qual é o índice do slot" é função pura em core/dragdrop, com teste — pelo motivo que o KDoc de DashboardEditLayout dá para si: expensive to prove through a screen and cheap to prove here. O projeto só tem jvmTest; tudo o que puder ser aritmética sem Compose, é.

Maestro

  • .maestro/flows/dashboard/customization.yaml é reescrito, não remendado: seus sete usos de dashboard_edit_section_header, os dois comandos em massa e a leitura "acima/abaixo do cabeçalho = ativo/não" não têm tradução.
  • Nova leitura: está em dashboard_edit_item_<key> na lista, ou em dashboard_showcase_item_<key> na vitrine — nunca nos dois. Incluir é um swipe para cima a partir do ≡ do card na vitrine; remover, um swipe para baixo do ≡ do item até o peek.
  • O estado vazio fica mais caro de alcançar. Hoje o flow chega a dashboard_empty_edit com um toque em "Remover todos"; sem ele, são tantos arrastos quantos widgets o layout padrão tem. A change decide se o flow paga esse preço ou se o estado vazio passa a ser coberto por outro caminho — é um custo do flow, não do produto.
  • O trecho das opções muda só o alvo — a sheet do ModalManager já expõe tags.
  • A entrega inclui rodar no AVD pixel_6 API 36 e dizer em qual dispositivo foi, como o .maestro/README.md cobra.

  • test tagsdashboard_component_${key} · dashboard_edit_item_${key}lidas pelo Maestro

Duplicar hoje daria crash na LazyColumn, config de um sobrescrevendo a do outro, e tags ambíguas para o Maestro. Vai precisar de um id persistido por instância; o tamanho está medido no quadro acima. Uma ideia que valeu registrar: id = type para o que já está salvo e type-2, type-3… para as demais mantém o layout padrão com as mesmas tags e dá ao Maestro um id alcançável.
